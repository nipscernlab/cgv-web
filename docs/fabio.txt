Updated by Luciano Manhaes De Andrade Filho about 2 months ago

Hi Fabio and everyone,

Thanks for the follow-up.

Here is the current data flow in more detail.

The application retrieves event data from the ATLAS Live service hosted at:

https://atlas-live.cern.ch

The frontend first requests:

https://atlas-live.cern.ch/latest

This endpoint returns the reference to the most recent JiveXML event file.
The application then extracts the corresponding XML path and requests the actual event file from atlas-live.cern.ch.

A typical flow looks like this:

Client application → https://atlas-live.cern.ch/latest → JiveXML_<event>.xml on atlas-live.cern.ch

Example:

https://atlas-live.cern.ch/latest

→ returns reference to something like:

https://atlas-live.cern.ch/event-files/.../JiveXML_XXXXXXXX.xml

At the moment, there is an additional Cloudflare Worker proxy in front of these requests:

https://atlas-cors-prox.nipscernlab.workers.dev/

This proxy was introduced only to solve browser CORS restrictions during external development/testing. It does not store or modify any data.

Its behavior is very restricted:

    it only accepts GET requests
    it only forwards requests to atlas-live.cern.ch
    any other destination is rejected
    no data is persisted
    caching is disabled

So the current implementation is:

Client → Cloudflare Worker → atlas-live.cern.ch → JiveXML file

However, if deployment inside ATLAS/P1 requires avoiding external services, this proxy can be removed and replaced with an internal CERN-hosted proxy or direct access, depending on your network/security requirements.

The actual event source remains entirely within ATLAS infrastructure (atlas-live.cern.ch).

Best regards,
Luciano

Hi Fabio,

Thank you again for your patience with this deployment. I'd like to give you full context on how the application is structured so you have everything you need to align it with the P1 infrastructure, and so we can resolve both the v1.0.3 regression and the live-folder feature in one go.

Architecture
The application has two completely independent components:

Static frontend (plain HTML/JS/CSS plus the calorimeter geometry binary and the WASM event-ID parser). These are pure files on disk under /var/www/cgv-web/public/ (entry point: index.html). Nothing dynamic. Apache can serve them directly, no backend required.

Python backend (/var/www/cgv-web/server.py) — a small http.server-based service running on 127.0.0.1:8080. Its only purpose is to expose four read-only endpoints under /api/xml/* that list and stream JiveXML files from a configured directory on disk. It is not involved in serving the static site.

The frontend calls /cgv-web/api/xml/list and /cgv-web/api/xml/file/<name> to populate the "SERVER" sub-mode of the sidebar (the live-folder feature). Apache is expected to reverse-proxy that single prefix to the local backend; everything else under /cgv-web/ is served as static files.

A minimal Apache configuration that matches this layout is:

Alias /cgv-web/ /var/www/cgv-web/public/
<Directory /var/www/cgv-web/public/>
Require all granted
</Directory>
ProxyPass /cgv-web/api/xml/ http://127.0.0.1:8080/api/xml/
ProxyPassReverse /cgv-web/api/xml/ http://127.0.0.1:8080/api/xml/

What went wrong in v1.0.3
That version was the first to ship /etc/httpd/conf.d/cgv-web.conf and to call systemctl reload httpd in the post-install script. Looking at it again, the snippet only contains the ProxyPass directives, that is, it has no Alias for the static files. If the working configuration you had in place for v04.28.26/v1.0.2 was the one providing the Alias, the new file would not have removed it on its own, but the automatic reload combined with whatever ordering Apache picked may well have left the static side without a route.

In short, v1.0.3 made assumptions about your Apache setup that I should not have baked into the RPM. I will fix this in v1.0.4 by:

removing /etc/httpd/conf.d/cgv-web.conf from the package
shipping the same snippet as /var/www/cgv-web/examples/apache-cgv-web.conf.example (documentation only, never loaded)
removing the automatic systemctl reload httpd
keeping the rest of v1.0.3's improvements (auto-start of the systemd unit, /etc/sysconfig/cgv-web for runtime overrides, backend bound to 127.0.0.1)

This way the RPM only delivers files and the systemd unit. Apache configuration stays entirely under your (and Puppet's) control.

What is needed to make the live-folder feature work:
The Python backend reads from the path given by the XML_FOLDER environment variable in /etc/sysconfig/cgv-web. For P1 the natural target is /atlas/EventDisplayEvents, which you mentioned is auto-mounted on the pc-atlas-cr-* nodes but not on vm-calo-web-01.

The single missing piece on the infrastructure side is therefore: could /atlas/EventDisplayEvents be mounted read-only on vm-calo-web-01 (via the same automount/NFS mechanism used on the CR nodes, or any equivalent)? Once that path is reachable from the VM, the backend can serve the files transparently and the SERVER mode in the UI will work end-to-end without any CERN-external traffic.

Hi Fabio, Diana,

Thanks for installing 2.0.1. The static site is served correctly, but LIVE > SERVER (the live-folder feature) is still not working, and we have now pinned down why.

That mode is enabled by a single request from the frontend, GET /cgv-web/api/xml/folder, which has to reach the Python backend and return JSON. We checked it from outside, through the AtlasGW proxy, and it comes back as:

HTTP/1.1 404 Not Found
    Server: Apache/2.4.62 (AlmaLinux)
    Content-Type: text/html; charset=iso-8859-1

So Apache itself is answering the API path with its own 404, which means the request never reaches the backend.

Looking at the config from note #42:

Alias /cgv-web/ /var/www/cgv-web/public/
    &lt;Location /var/www/cgv-web/public/&gt;
        ProxyPass        http://vm-calo-web-01.cern.ch:8080/
        ProxyPassReverse http://vm-calo-web-01.cern.ch:8080/
    &lt;/Location&gt;

the argument of <Location> is a filesystem path, but <Location> matches a URL path. Requests arrive as /cgv-web/..., never as /var/www/cgv-web/public/, so the ProxyPass inside that block never matches. The Alias still serves the static files (that is why the site loads), but /cgv-web/api/xml/ falls through to a static lookup and 404s.

The backend serves both the static site and /api/xml/ from the same root, so the simplest fix is one proxy for the whole prefix, no Alias:

&lt;Location /cgv-web/&gt;
        ProxyPass        http://127.0.0.1:8080/
        ProxyPassReverse http://127.0.0.1:8080/
        Require all granted
    &lt;/Location&gt;

If you prefer Apache to keep serving the static files, the alternative is to
proxy only the API, declared before the Alias so it takes precedence:

ProxyPass        /cgv-web/api/xml/ http://127.0.0.1:8080/api/xml/
    ProxyPassReverse /cgv-web/api/xml/ http://127.0.0.1:8080/api/xml/
    Alias /cgv-web /var/www/cgv-web/public
    &lt;Directory /var/www/cgv-web/public&gt;
        Require all granted
    &lt;/Directory&gt;

One detail on the target: the backend listens on 127.0.0.1:8080 (BIND in /etc/sysconfig/cgv-web). The 127.0.0.1 targets above assume the Apache that exposes cgv-web runs on vm-calo-web-01. If it runs on a different host, set BIND=0.0.0.0 in /etc/sysconfig/cgv-web, run systemctl restart cgv-web, and point the ProxyPass at vm-calo-web-01.cern.ch:8080 instead.

A 30-second check from the VM:

curl -s -i http://127.0.0.1:8080/api/xml/folder
    curl -s -i https://pc-atlas-www.cern.ch/cgv-web/api/xml/folder

The first is the backend (expect 200 + application/json + {"path": ...}); the second is through Apache and should match. Once the second returns JSON, the folder control appears in the UI and we can point it at /atlas/EventDisplayEvents.

Separately, we built cgv-web-2.1.0 (frontend only, in-place upgrade, no change to the backend, the systemd unit or the packaging). It does not change the fix above. It just stops the failure from being silent: when /api/xml is unreachable on a cern.ch host, the SERVER panel now shows a short notice instead of hiding the control, and it re-checks /api/xml when the SERVER tab is opened, so the control shows up as soon as the proxy is in place.
